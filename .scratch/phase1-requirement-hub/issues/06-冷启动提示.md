### 这个工单要做什么（一句话）

让会议里提取的 **issue 类条目**（遗留问题、风险、用户痛点）一键进入反馈模块参与 AI 聚类，而不是 PM 手动复制粘贴。流程：会议详情页选 issue 条目 → 点"转入反馈" → 系统新建一条 feedback_analysis（source_label 标注"来自会议《X》"）+ 批量写 feedback_items（source_type='meeting'，source_meta 记 meeting_id + meeting_item_id）→ 触发 feedback-analyze 聚类 → 原会议条目标记 transferred_to_feedback=true 并显示"已转入反馈 →"溯源角标。

### ⚠️ 上手前必读：ADR-0002 的三条硬约束（决定性，违反即返工）

**`docs/adr/0002-meeting-feedback-via-cluster.md`** 必须先读，它定义了三条不可妥协的边界：

1. **只转 issue，不转 requirement** —— 会议条目有四类（decision/todo/requirement/issue），**只有 category='issue' 的能转**。requirement 类不转（那会污染聚类，因为 requirement 是结构化需求，不是反馈噪声）。UI 上只有 issue 类条目显示"转反馈"按钮。

2. **Copy 快照语义，单向不可逆** —— 转入是"复制一份快照"到反馈模块，转入后双方独立编辑互不同步：
   - 转入后编辑会议条目 → **不影响** feedback_item
   - 删除 feedback_item → **不影响**会议条目
   - source_meta 记录的 meeting_item_id 是**溯源链接**（查出身用），**不是同步契约**。工单验收明确要验证这条（"Copy 语义验证"）。

3. **Phase 1 每次新建独立 analysis** —— 每次转入都新建一条 feedback_analysis，不复用已有的。多源合并（同一条反馈来自多个会议）defer 到 Phase 2。本工单不做"合并到已有 analysis"的逻辑。

还要读：

**`supabase/functions/feedback-analyze/index.ts` 现状**（06 必须改造，工单第 16 行硬要求）：
- 当前入参：`{ analysisId, items }`，items 是字符串数组
- 聚类后 update feedback_items.topic_id + sentiment
- **06 必须改造**：让 EF 接受**预置 sourceItems** 入参（带 source_type/source_meta 的对象数组，不是裸字符串）。即使 feedback_items 已在 action 层插库带 source_meta，工单 checklist 第 16 行明确写"接受预置 sourceItems 入参，写入时带 source_type/source_meta"——这是验收项，必须做。
  - 具体改法：EF 的入参从 `{ analysisId, items: string[] }` 扩展为 `{ analysisId, items: string[], sourceItems?: Array<{ content: string; source_type?: string; source_meta?: Record<string, unknown> }> }`
  - **action 改传 sourceItems**：第 6 步调用时，body 改成传 sourceItems（带 source_type/source_meta 的对象数组），不再传裸字符串 items（或者两个都传，EF 内部兼容）
  - **核查现有 EF 如何 update topic_id**：如果 EF 是用传入 items 的下标去匹配 feedback_items（按插入顺序），那 sourceItems 的顺序必须与 feedback_items 插入顺序一致；如果 EF 是按 analysis_id 重新查 feedback_items 来 update，那只需保证聚类 prompt 用 sourceItems[i].content 即可。读完整 EF 确认匹配方式。
  - **建议**：先读完整 EF（全文），看它如何把聚类结果落回 feedback_items。这决定改造的具体改法（是否要保留 items 字符串数组的兼容性，还是直接换 schema）。

**溯源角标精确跳转的 design（工单第 13 行硬要求）**：角标点击必须跳到**对应的 feedback_analysis 详情页**（`/dashboard/feedback/[analysisId]`），不是列表页。问题是 meeting_items.transferred_to_feedback 只是 boolean，没存 analysis_id。两条实现路径：
- **方案 A（推荐，不改 schema）**：角标渲染时，通过 source_meta 反查——feedback_items 里有 `source_meta.meeting_item_id = 当前 item.id` 的那条，取它的 `analysis_id`。可以在 server component 层把"已转入条目的 analysis_id 映射"一次性查出来传给 MeetingItemCard（按 meeting_id 查所有 source_type='meeting' 且 source_meta->meeting_id 匹配的 feedback_items，建 `meeting_item_id → analysis_id` map）。
- 方案 B：在 meeting_items 加 transferred_analysis_id 字段。但要改迁移（违反"不改迁移"）。
- **选方案 A**。在会议详情页 server component 层加一次查询：`feedback_items` where `source_type='meeting'` 且 `source_meta->meeting_id = meetingId`，select `analysis_id, source_meta`，在内存里构建 `{ [meeting_item_id]: analysis_id }` 映射，传给 issue 分组的 MeetingItemCard。角标 href 指向 `/dashboard/feedback/[analysisId]`。
- **前提**：反馈详情页路由存在（核查 `src/app/dashboard/feedback/[analysisId]/page.tsx` 是否存在；如不存在，跳转到 `/dashboard/feedback?analysis=xxx` 也是可接受的近似，但要核查后再定）。

### 实现导航：核心是新 server action

#### 核心扩展点：`transferMeetingItemsToFeedback` action

仿 `createFeedbackAnalysis` 的结构（同文件），但来源是会议条目：

```typescript
/** 会议 issue 条目批量转入反馈聚类池（06 工单，遵循 ADR-0002） */
export async function transferMeetingItemsToFeedback(
  projectId: string,
  meetingId: string,
  itemIds: string[]
): Promise<{ ok: true; analysisId: string } | { ok: false; error: string }> {
  const supabase = await createSupabaseActionClient();
  const { data: { user } } = await supabase.auth.getUser();
  if (!user) return { ok: false, error: "未登录" };
  if (!projectId) return { ok: false, error: "请先选择项目" };
  if (itemIds.length === 0) return { ok: false, error: "请至少选择一个条目" };

  // 1. 查会议条目，校验：都属于该 meeting + category='issue' + 未转
  const { data: items } = await supabase
    .from("meeting_items")
    .select("id, content, category, transferred_to_feedback, meeting_id")
    .in("id", itemIds);
  
  const valid = (items ?? []).filter(it =>
    it.meeting_id === meetingId &&
    it.category === "issue" &&
    !it.transferred_to_feedback
  );
  if (valid.length === 0) return { ok: false, error: "没有可转入的 issue 条目（可能已转入或非 issue 类）" };

  // 2. 取会议标题
  const { data: meeting } = await supabase
    .from("meetings")
    .select("title")
    .eq("id", meetingId)
    .single();
  const meetingTitle = meeting?.title ?? "未命名会议";

  // 3. 建 feedback_analysis（source_label 标注来源）
  const { data: analysis, error: analysisErr } = await supabase
    .from("feedback_analyses")
    .insert({
      user_id: user.id,
      project_id: projectId,
      title: `来自会议《${meetingTitle}》的反馈`,
      source_label: `来自会议《${meetingTitle}》`,
      input_mode: "paste",
      total_count: valid.length,
      status: "analyzing",
    })
    .select()
    .single();
  if (analysisErr || !analysis) return { ok: false, error: "创建反馈分析失败" };

  // 4. 批量插 feedback_items（source_type='meeting' + source_meta 溯源）
  const itemRows = valid.map(it => ({
    analysis_id: analysis.id,
    user_id: user.id,
    content: it.content,
    source_type: "meeting",
    source_meta: { meeting_id: meetingId, meeting_item_id: it.id },
  }));
  const { error: itemsErr } = await supabase.from("feedback_items").insert(itemRows);
  if (itemsErr) return { ok: false, error: "保存反馈条目失败" };

  // 5. 标记会议条目已转入（transferred_to_feedback=true）
  const { error: markErr } = await supabase
    .from("meeting_items")
    .update({ transferred_to_feedback: true })
    .in("id", valid.map(it => it.id));
  // 标记失败不阻塞（feedback 已建好），但记日志
  if (markErr) console.error("标记 transferred_to_feedback 失败:", markErr);

  // 6. 调 feedback-analyze EF 触发聚类（传 sourceItems，EF 改造后接受预置来源）
  try {
    const res = await fetch(`${publicEnv.supabaseUrl}/functions/v1/feedback-analyze`, {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        Authorization: `Bearer ${(await supabase.auth.getSession()).data.session?.access_token ?? ""}`,
      },
      body: JSON.stringify({
        analysisId: analysis.id,
        // 传预置 sourceItems（带 source_type/source_meta），EF 改造后据此聚类
        sourceItems: valid.map(it => ({
          content: it.content,
          source_type: "meeting",
          source_meta: { meeting_id: meetingId, meeting_item_id: it.id },
        })),
      }),
    });
    if (!res.ok) {
      await supabase.from("feedback_analyses")
        .update({ status: "failed", error_message: "AI 聚类服务暂不可用" })
        .eq("id", analysis.id);
    }
  } catch {
    await supabase.from("feedback_analyses")
      .update({ status: "failed", error_message: "网络异常，请重试" })
      .eq("id", analysis.id);
  }

  revalidatePath(`/dashboard/meetings/${meetingId}`);
  revalidatePath("/dashboard/feedback");
  return { ok: true, analysisId: analysis.id };
}
```

**关键设计点**：
- 步骤 4 插 feedback_items 时就带 source_type/source_meta（Copy 快照写入点）
- 步骤 5 标记 meeting_items 是独立 update，**不影响已插的 feedback_items**（Copy 语义：双方独立）
- 步骤 6 调 EF 时传 sourceItems（带来源元数据的对象数组），EF 改造后接受这个新入参。这是工单 checklist 第 16 行硬要求，不能省。
