### 实现范围（严格边界——只做这些）

**① 新建 `supabase/migrations/007_v2_requirement_hub.sql`**，内容：
- 新增枚举 `requirement_lifecycle`（draft/confirmed/in_progress/delivered/parked）
- `requirement_drafts` 加字段：`priority`（priority_level，默认 medium）、`lifecycle`（requirement_lifecycle，默认 draft）、`source_meeting_item_id`（uuid references meeting_items，on delete set null）、`deleted_at`（timestamptz）
- `api_drafts` 加字段：`source_requirement_id`（uuid references requirement_drafts，on delete set null）+ 对应索引
- 保守回填：老数据 `lifecycle` 统一置 'draft'（**不要**自动置 confirmed——遵循"强制 PM 走查"原则）
- 来源一致性 check 约束：source_type='feedback_topic' 时 source_topic_id 非空；source_type='meeting_item' 时 source_meeting_item_id 非空
- 修复 v1 K-1：`projects` 加 `check (length(btrim(name)) > 0)`
- `profiles` 加 `feature_flags jsonb not null default '{}'`
- 软删索引：`requirement_drafts(project_id, lifecycle, priority) where deleted_at is null`

**② 新建 `supabase/migrations/008_v2_feedback_source.sql`**，内容：
- `feedback_items` 加 `source_type text not null default 'paste'` + `source_meta jsonb`
- `feedback_analyses` 加 `source_label text`
- `meeting_items` 加 `transferred_to_feedback boolean not null default false` + 对应索引

**③ 更新 `src/types/database.ts`**，给这些 interface 加新字段（保持与迁移同步）：
- `RequirementDraft`: + priority / lifecycle / source_meeting_item_id / deleted_at
- `ApiDraft`: + source_requirement_id
- `MeetingItem`: + transferred_to_feedback
- `FeedbackItem`: + source_type / source_meta
- `FeedbackAnalysis`: + source_label
- 新增 `RequirementLifecycle` 类型

### 工作方式要求

- **用 `/tdd` 思路**：虽然这个工单主要是 SQL 迁移（没有纯函数可测），但 TS 类型更新后要跑 typecheck 确认不破坏现有代码。如果发现有可测的纯函数（比如 lifecycle 合法性校验），先写测试再实现——但注意 lifecycle 流转校验逻辑（canTransition）是 **03 工单**的范围，本工单**不要提前实现**，只做 schema + 类型。
- **定期跑 `npm run typecheck`**：每次改 TS 类型后跑一次，确认 0 错误。
- **最后跑完整测试套件** `npm run test`，确认 v1 的 150 个单测仍全通过（additive change 不应破坏任何现有测试）。
- **不要跑 `supabase db push`**：迁移文件写好即可，不要执行到任何真实数据库（本地或生产）。执行迁移是上线环节的事，不是本工单的事。
- **完成后用 `/code-review` 审查**这次工作（对 diff 做 Standards + Spec 双轴 review），然后把工作提交到当前 branch。
