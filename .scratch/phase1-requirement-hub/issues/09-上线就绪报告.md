## 1. 灰度机制说明

**单一模块级 flag：`requirement_hub`**（`profiles.feature_flags` jsonb）。Phase 1 新功能共用一个开关——灰度节奏是"先白名单、第 2 周全量"，按功能拆 key 无收益；未来需要细粒度时 jsonb 天然支持扩展（`FeatureFlags` 接口加字段即可）。

### 1.1 三层 gate

| 层 | 机制 | 位置 |
|---|---|---|
| ① 入口渲染 | layout 一次查询 flags → DashboardShell → Sidebar 按 `flag: "requirementHub"` 过滤 NAV_ITEMS，"需求"入口不渲染 | `src/app/dashboard/layout.tsx` → `src/components/dashboard/sidebar.tsx` |
| ② 页面占位 | requirements 列表/详情页 server 端 gate，flag off 渲染"功能尚未开放"（`FeatureUnavailable`），不触达数据层 | `src/app/dashboard/requirements/page.tsx`、`[requirementId]/page.tsx` |
| ③ action 二次校验 | 7 个写操作开头读 flags，off 直接拒绝（防绕过前端直调） | 见 1.2 |

会议详情页"批量转反馈"按钮：页面（server）读 flags 条件渲染（`src/app/dashboard/meetings/[meetingId]/page.tsx`），action 侧另有 1.2 第 6 项兜底。

## 3. 发现并处置的问题（均已闭环）

### 3.1 🔴→✅ profiles 表从未开启 RLS（002/004 疏漏）——已修复并实证

`004_rls.sql` 注释声称"全表 RLS"，但 002 建的 `profiles` 表未在 004 中 enable——该表含 `email` 与 007 的 `feature_flags`。**修复前实测**：anon key（无任何登录）`GET /rest/v1/profiles` 返回 200 + 2 行（含两个测试账号 email）；用户 A 的登录会话可把自己的 `feature_flags` 直接 PATCH 成 `requirement_hub:true`（自提权）、也能读到 B 的 profile 行。处置：

- `009_profiles_rls.sql`：`enable row level security` + `profiles_select_own`（`id = auth.uid()`），经 `supabase db push --linked` 应用到远程 DB。
- **修复后实测**：anon GET profiles → **0 行**；集成 check 15b（自改无效，PATCH 影响 0 行）、15e（A 查不到 B）转绿。
- 兼容性核对过：注册触发器 `fn_handle_new_user` 是 security definer（不受影响）；白名单 update 走 SQL Editor/service_role（bypass RLS）；应用侧 `loadFeatureFlags` 以自身会话读自己一行，策略放行。

### 3.2 🔴→✅ 远程 Supabase 项目一度不可达——用户已恢复

`.env.local` 指向的 `https://kcpcqocxtkaygtcpmmfp.supabase.co` 在本工单首日（08-18 上午）经本机 DNS + 阿里公共 DNS + AliDNS DoH 三方确认 NXDOMAIN（项目暂停/删除态）。**用户当日恢复项目后**：数据完整（projects/meetings/api_drafts/feedback_analyses 与 007 新列全在），集成测试与 UI 验证随即全部完成。后续注意：free tier 项目长期不活动会再暂停，上线前建议确认项目活跃状态（恢复后域名即时生效，无需改 `.env.local`）。
