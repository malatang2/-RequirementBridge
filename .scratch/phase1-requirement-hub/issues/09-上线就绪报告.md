## 1. 灰度机制说明

**单一模块级 flag：`requirement_hub`**（`profiles.feature_flags` jsonb）。Phase 1 新功能共用一个开关——灰度节奏是"先白名单、第 2 周全量"，按功能拆 key 无收益；未来需要细粒度时 jsonb 天然支持扩展（`FeatureFlags` 接口加字段即可）。

### 1.1 三层 gate

| 层 | 机制 | 位置 |
|---|---|---|
| ① 入口渲染 | layout 一次查询 flags → DashboardShell → Sidebar 按 `flag: "requirementHub"` 过滤 NAV_ITEMS，"需求"入口不渲染 | `src/app/dashboard/layout.tsx` → `src/components/dashboard/sidebar.tsx` |
| ② 页面占位 | requirements 列表/详情页 server 端 gate，flag off 渲染"功能尚未开放"（`FeatureUnavailable`），不触达数据层 | `src/app/dashboard/requirements/page.tsx`、`[requirementId]/page.tsx` |
| ③ action 二次校验 | 7 个写操作开头读 flags，off 直接拒绝（防绕过前端直调） | 见 1.2 |

会议详情页"批量转反馈"按钮：页面（server）读 flags 条件渲染（`src/app/dashboard/meetings/[meetingId]/page.tsx`），action 侧另有 1.2 第 6 项兜底。

### 1.2 gated server action 清单（7 处）

| # | Action | 文件 | off 时行为 |
|---|---|---|---|
| 1 | listRequirements | `src/app/dashboard/requirements/actions.ts` | 返回 `[]`（返回类型是数组，页面层另有占位 gate） |
| 2 | createRequirement | 同上 | `{ok:false, error:"该功能尚未开放"}` |
| 3 | updateRequirement | 同上 | 同上 |
| 4 | deleteRequirement | 同上 | 同上 |
| 5 | confirmRequirement | 同上 | 同上 |
| 6 | transferMeetingItemsToFeedback | `src/app/dashboard/feedback/actions.ts` | 同上 |

**不 gate（有意）**：`regenerateApiDraft` / `saveVersion` / feedback 其余 action（v1 原有功能）；07 的分组视图 `?view=grouped`（纯只读，非白名单用户无 source_requirement_id 数据，自然全部落在"未归属"，无害）。

### 1.3 核心实现

- `src/lib/feature-flags.ts`：
  - `parseFeatureFlags(raw)` 纯函数，**fail closed**——null/非对象/数组/非严格 `=== true` 一律关，其他 key 忽略；12 个单测覆盖（`src/lib/__tests__/feature-flags.test.ts`）。
  - `loadFeatureFlags(client)` 读取 helper（server client / action client 均可传）：`auth.getUser()` → `from("profiles").select("feature_flags").eq("id", user.id)` → parse；未登录/查无行/查询失败均视为关。
- `src/types/database.ts`：补 `Profile` 接口（此前文件无任何 Profile 类型）。

### 1.4 flag off / on 验证方式

- **解析语义**：vitest 12/12（null/undefined/数组/字符串/数字/布尔/空对象/`true`/`false`/非严格 true/其他 key/不可变返回）。
- **数据链路**（flag off → 白名单 → on → 隔离）：集成脚本新增 **check 15**（`scripts/integration-check.mjs`，5 个子断言：15a 默认关 / 15b 防提权（用户会话自改 flags 无效）/ 15c 白名单生效 / 15d 非白名单对照 / 15e profiles 跨用户 RLS）。**本次因远程 DB 不可达未能执行**（见 §4），DB 恢复后运行即得双向验证。
- **action 层防绕过**：server action 无法从 node 脚本直调（Next.js RPC 需构建产物内的 action id）。gate 实现是 action 开头对 `loadFeatureFlags` 结果的早退——该函数的数据链路由 check 15 验证、解析语义由单测验证；action 早退分支为纯控制流（`if (!featureFlags.requirementHub) return {...}`）。UI 层实机验证（登录后点按）需 DB 恢复后进行。

## 3. 发现并处置的问题

### 3.1 🔴 profiles 表从未开启 RLS（002/004 疏漏，已写 009 迁移）

`004_rls.sql` 注释声称"全表 RLS"，但 002 建的 `profiles` 表未在 004 中 enable——该表含 `email` 与 007 的 `feature_flags`，RLS 关闭意味着**持有 anon key 即可经 PostgREST 读取全部用户资料**（本次无法实测取证，因项目本身不可达；见 §4）。处置：

- 新增迁移 `supabase/migrations/009_profiles_rls.sql`：`enable row level security` + `profiles_select_own`（`id = auth.uid()`）。
- 兼容性已核对：注册触发器 `fn_handle_new_user` 是 `security definer`（不受 RLS 影响）；白名单 update 走 SQL Editor/service_role（bypass RLS）；应用侧 `loadFeatureFlags` 以自身会话读自己一行，策略放行。
- **未在会话内执行**（DB 不可达）——已列入 §7 上线手册第 6 步（必执行）；集成 check 15b/15e 会在 009 未执行时变红，作为防漏提醒。

### 3.2 🔴 远程 Supabase 项目不可达（环境阻断，非代码问题）

`.env.local` 指向的 `https://kcpcqocxtkaygtcpmmfp.supabase.co` 无法解析：

- `nslookup`（本机 DNS + 阿里公共 DNS 223.5.5.5 + AliDNS DoH）一致返回 **NXDOMAIN / Status 3**（域名不存在），而 `supabase.co` 顶级域正常解析——排除本地网络/DNS 污染，指向**项目已被删除或域名移除**（free tier 项目长期不活动会被暂停，暂停项目域名仍在；NXDOMAIN 更接近删除）。
- 08 报告（2026-08-04）时项目尚可用（`db push` + 集成 25/25 绿），时隔 14 天。
- 影响：集成测试、白名单 SQL 实际执行、flag on/off 实机验证、任何依赖远程 DB 的验证全部阻断。**恢复步骤见 §7 第 0 步。**

## 7. 上线操作手册（用户执行，agent 只写不做）

> 前提提醒：合并顺序与灰度节奏与 03-08 约定一致；agent 未做任何 git push / PR / 控制台操作。

**第 0 步（新增，本次阻断的恢复）——恢复或重建 Supabase 项目**

1. 登录 [Supabase Dashboard](https://supabase.com/dashboard) 查看 `kcpcqocxtkaygtcpmmfp` 项目状态：
   - 若 **paused**：Restore（恢复后域名恢复解析）。
   - 若已**删除**：新建项目 → 记下新的 URL/anon key/service_role key。
2. 若新建项目：`supabase link --project-ref <新ref>` 后 `supabase db push`（会按序执行 002→…→**009** 全部迁移；或在 Dashboard SQL Editor 逐个粘贴执行）。
3. 更新本地与 Vercel 的 `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` / `SUPABASE_SERVICE_ROLE_KEY`。
4. Edge Functions（meeting-analyze / api-generate / feedback-analyze / feedback-gen-requirement）需重新部署（`supabase functions deploy <name>`）。
5. 重跑 `node scripts/integration-check.mjs`——预期 **35/35 全绿**（08 时点 30 个断言 + check 15 新增 5 个）。若 15b/15e 红 = 009 未执行，回第 2 步。

**第 1 步 — push（顺序敏感）**

```
git push 依次：feat/03-requirement-crud-filter → feat/04-* → feat/08-regression → feat/09-feature-flag-release
（03 先于 04，否则 04 的 PR diff 会带上 03+#02 的 commit；
 feat/08-regression 已含 05/06/07，无需单独推这三条）
```

**第 2 步 — 合并 PR（顺序同上）**：03 → 04 → feat/08-regression → feat/09-feature-flag-release → main

**第 3 步 — Vercel 自动部署**：确认生产为 Phase 1 最新代码（K-5）。

**第 4 步 — 核对环境变量（K-2）**：`NEXT_PUBLIC_SUPABASE_*` / `SUPABASE_SERVICE_ROLE_KEY` / `DASHSCOPE_API_KEY` / `NEXT_PUBLIC_POSTHOG_KEY`。

**第 5 步 — 执行 009 迁移**（若第 0 步已随 db push 执行则跳过）：SQL Editor 粘贴 `supabase/migrations/009_profiles_rls.sql`。

**第 6 步 — 灰度白名单**：编辑 `scripts/whitelist-requirement-hub.sql` 填入白名单邮箱 → SQL Editor 执行 → 用白名单账号走一遍需求模块全链路（建需求→confirm→带入 API→会议条目转入）；非白名单账号确认侧栏无"需求"入口、直链显示"功能尚未开放"。

**第 7 步（非阻塞）— Google OAuth（K-3）**：Supabase 控制台 Auth → Providers → Google。

**第 8 步 — 第 2 周全量**：SQL Editor 执行 `update profiles set feature_flags = jsonb_set(feature_flags, '{requirement_hub}', 'true'::jsonb, true);`（或代码侧去掉 gate 后重新部署）。

**回滚预案**：代码回滚 = Vercel 即时回滚上一版本；灰度回滚 = 把白名单邮箱的 `requirement_hub` 置回 `false`（whitelist SQL 把 `'true'` 改 `'false'` 重跑）。
