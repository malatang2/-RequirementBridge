### 2.3 关键设计说明：真实用户 B 取代伪造 user_id

v1 集成脚本用 service_role 写"伪造 user_id 的行"模拟跨用户隔离。Phase 1 的 `requirement_drafts` / `api_drafts` 等表的 `user_id` 有 FK → `auth.users(id)`，伪造 UUID 不满足 FK（service_role 也写不进）；而 anon 会话塞伪造 user_id 又被 RLS `with check` 拒绝。因此 08 用 service_role 调 `/auth/v1/admin/users` **幂等创建一个真实用户 B**（`rb08-test-b@example.com`），让 B 用自己的登录会话写真实数据，制造"B 真实写了一行，A 的会话查不到"的合法跨用户场景——与 v1 既有 RLS 测试同等可信。

### 2.4 本轮发现并解决的 RLS 根因（记录，非 08 引入的 bug）

首次重写 check 11-14 时，所有 anon 会话的 insert 都 42501 失败。根因：`004_rls.sql` 所有业务表的 insert policy 是 `with check (user_id = auth.uid())`，而 PostgREST **不会**把 `auth.uid()` 自动填入插入行——必须在 body 里显式带 `user_id` 且值等于 JWT sub。修复：在 `runPhase1Checks` 顶部从 JWT 解出 `uidA`/`uidB`，所有 AUTH 插入 body 显式带 `user_id`。这是脚本侧的写法修正，**没有改动任何 RLS policy 或业务代码**——RLS 本身的行为是对的（前端的 server action 走 supabase-js 时 SDK 会带 user_id），只是本脚本直连 REST 时漏带了。
