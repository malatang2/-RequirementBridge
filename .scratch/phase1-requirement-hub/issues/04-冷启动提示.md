### 这个工单要做什么（一句话）

给 Requirement 加一道**人工确认关卡**：draft 状态的需求，PM 在详情页点"确认纳入需求池"按钮，lifecycle 流转为 confirmed；非法流转（如 delivered→draft）被 `canTransition` 纯函数拒绝。确认动作触发 `requirement_confirmed` 埋点（v2 北极星指标）。同时把 feedback-gen-requirement Edge Function 的写入显式改为 `lifecycle: "draft"`（让"AI 生成需人工确认"这个意图在代码里显式，不依赖 DB 默认值）。

这条关卡对应 ADR-0002 的信号降噪原则——只有经过人工拍板的才进 backlog，避免 AI 噪声污染需求池。

### 实现导航：照着同文件的现成模式扩展（重要——不要发明新模式）

本工单是**扩展 03 的代码**，所有模式都在同文件里有模板，严格照抄风格。

#### 扩展点一：canTransition 纯函数 —— 加到 `src/lib/requirements.ts`

仿同文件的 `validateRequirementInput` 的风格（纯函数 + 判别返回）。设计要点：

1. 先定义合法流转表（`TRANSITIONS` 常量，`Record<RequirementLifecycle, RequirementLifecycle[]>`）：
   - **工单明确要求的路径**：`draft → confirmed`（✓ 这是本工单 UI 要用的）
   - **完整合法路径集**（为未来工单铺路，但本工单 UI 只用 draft→confirmed）：
     - `draft → confirmed`、`draft → parked`
     - `confirmed → in_progress`、`confirmed → parked`
     - `in_progress → delivered`、`in_progress → parked`
     - `delivered →` （终态，无出度）
     - `parked →` （终态，无出度）
   - **非法路径**（canTransition 必须拒绝）：`delivered → draft`、`confirmed → draft`、任意回退、任意跨级跳跃
2. `canTransition(from: RequirementLifecycle, to: RequirementLifecycle): boolean` 纯函数
3. 可选：`describeTransition(from, to): { ok: true } | { ok: false; error: string }` —— 给 action 层返回错误文案用（仿 validateRequirementInput 的判别联合风格）。如果觉得 canTransition 够用，也可以让 action 层自己组装错误文案，二选一，保持简洁。

#### 扩展点二：confirmRequirement action —— 加到 `src/app/dashboard/requirements/actions.ts`

仿同文件的 `updateRequirement` 的五段式结构：
1. 调 `canTransition(requirement.lifecycle, "confirmed")` 校验（先 select 出当前 lifecycle）
2. 鉴权 `supabase.auth.getUser()`
3. DB update lifecycle='confirmed' + revalidatePath
4. **触发埋点**：`await track("requirement_confirmed", { requirementId: id, sourceType: requirement.source_type, projectId: requirement.project_id })`

命名建议 `confirmRequirement(id)`（专一清晰），而非泛化的 `transitionRequirement(id, to)`——因为本工单只做 draft→confirmed 这一个流转，UI 只有一个按钮。泛化设计等未来真有多流转 UI 时再重构（YAGNI）。

埋点注意：`track()` 是异步浏览器端函数，在 server action 里调用要 `await import("@/lib/analytics")` 动态引入（参考 `src/app/(auth)/actions.ts` 里 `signInWithEmail` 怎么调 `identifyUser` 的——`const { identifyUser } = await import("@/lib/analytics")`）。但注意 server action 跑在服务端，`track()` 内部 `typeof window === "undefined"` 会直接 return null——所以 server action 里的 track 实际是 no-op。**正确的埋点点应该在客户端组件里**（RequirementEditor 的 onClick 成功回调里调 track），不是 server action 里。看现有代码 `meetings/new/page.tsx` 怎么在客户端调 track 的就懂了。

#### 扩展点三：Confirm 按钮 —— 加到 `src/components/dashboard/requirement-editor.tsx`

仿同组件现有的"删除"按钮（`handleDelete` + `useTransition` + `disabled={isPending}`）。在 viewing 模式的按钮区（CopyButton 之后、编辑按钮之前）插入：

```tsx
{requirement.lifecycle === "draft" && (
  <button
    type="button"
    onClick={handleConfirm}
    disabled={isPending}
    className="rounded-md bg-primary px-3 py-1.5 text-sm text-primary-foreground hover:bg-primary/90 disabled:opacity-50"
  >
    {isPending ? "确认中…" : "确认纳入需求池"}
  </button>
)}
```

`handleConfirm` 函数：调 `confirmRequirement(requirement.id)`，成功后**在客户端调 `track("requirement_confirmed", {...})`**（这是埋点的正确位置），失败 setError。成功后页面会因 revalidatePath 自动刷新显示新 lifecycle。

#### 扩展点四：feedback-gen-requirement EF 改一行

文件：`supabase/functions/feedback-gen-requirement/index.ts`
现状：insert requirement_drafts 时**没写 lifecycle**（依赖 DB 默认值 'draft'）。
改动：insert 对象里**显式加 `lifecycle: "draft"`**。这行改动让"AI 生成的草稿需人工确认"这个业务意图在 EF 代码里显式可见，不依赖隐式 DB 默认。改完跑 `npm run lint` 确认 EF 不报错（EF 是 Deno runtime，tsc 不检查，但 lint 会扫）。
