## 3. 数据来源与去向（全局视图）

### 3.1 数据来源（输入）

| 来源 | 形态 | 进入方式 | 落库位置 |
|---|---|---|---|
| 用户粘贴的会议文本 | string | 文本模式表单 | `meetings.raw_text` |
| 用户上传的会议音频 | binary（≤50MB，mp3/wav/m4a） | 前端直传 Storage | `meetings.audio_path` + Storage `meeting-audio/` |
| 用户业务需求描述 | string | 模块二表单 | `api_drafts.business_requirement` |
| 用户反馈（粘贴/CSV/TXT） | string[] / file | 模块三表单 | `feedback_items.content` + Storage `feedback-files/` |
| DashScope ASR 结果 | text | Edge Function 回填 | `meetings.raw_text`（覆盖/填充） |
| DashScope Qwen 生成 | JSON / YAML | Edge Function 解析后 | `meeting_items` / `api_drafts.current_yaml` / `feedback_topics` |

### 3.2 数据去向（输出）

| 去向 | 形态 | 生成方式 | 边界说明 |
|---|---|---|---|
| 浏览器展示 | UI（四类条目/卡片/图表） | 前端从 DB 读取渲染 | 仅本人（RLS） |
| 导出文件 | MD/CSV/YAML/JSON | **前端纯函数生成**（`meetings.ts:240-297`） | SOW §3：唯一外溢通道 |
| 剪贴板 | text | 浏览器复制 API | 同上 |
| Postgres 留存 | DB 行 | SDK / Edge Function 写入 | 按用户隔离，v1 无定时清理（DM-4：保留期随业务可删） |

> **关键边界**：**数据不自动流向任何外部业务系统**（Jira/飞书/Linear 等均不直连，SOW §3 第 2、5 条）。所有"对外"动作都由人确认 + 手动导出。

| 字段 | 方向 | 类型 | 说明 |

### 4.3 Edge Function 统一 I/O 约定（接口契约 §0.2）

**请求**：`POST /functions/v1/<name>`，header `Authorization: Bearer <supabase_access_token>`，body JSON。

**响应**（成功）：
```json
{ "success": true, "data": { ... }, "error": null }
```
**响应**（失败）：
```json
{ "success": false, "data": null,
  "error": { "code": "LLM_TIMEOUT", "message": "...", "details": { "retryable": true } } }
```

## 5. 现有系统接入方式 + MCP/API/CLI 选择依据

### 5.1 现状总表（诚实盘点）

| 接入通道 | 应用对外（第一层） | 研发协作（第二层） | 当前状态 |
|---|---|---|---|
| **MCP** | ❌ 无 MCP server | ❌ 未引入 | 未实现 |
| **API（REST/HTTP）** | ⚠️ 3 个内部 Edge Function（仅供自家前端，**非开放 API**） | ✅ Supabase Management API（控制台操作） | 部分实现 |
| **CLI** | ❌ 无应用 CLI | ✅ git / npm / supabase CLI / 飞书 CLI | 已用于研发 |
| **SDK 直连** | ✅ Supabase JS SDK（前端 CRUD，RLS 保护） | — | 已实现 |
| **文件导出** | ✅ MD/CSV/YAML/JSON（唯一对外数据通道） | — | 模块一已实现 |

> **重要澄清**：应用的 Edge Function（`meeting-extract` 等）虽然走 HTTP，但**不作为开放 API 对外提供**——它们只接受带本系统 access_token 的内部调用（接口契约 §0.1）。v1 没有"第三方系统通过 API 接入需求桥"这个能力，这是 SOW §3 明确的范围外。

### 5.2 API（内部 Edge Function）—— 已用

**为什么用 Edge Function 而不是前端直调 AI**：
- **密钥隔离**：DashScope key 绝不进前端（接口契约 §0.1）。Edge Function 在 Deno 服务端持有 `DASHSCOPE_API_KEY`，前端只持 Supabase access_token（`supabase/functions/_shared/supabase.ts:27`）。
- **后处理需要服务端**：quote_offset 计算、JSON 容错解析、swagger-parser 校验等须在可信环境执行。
- **状态机编排**：ASR 异步轮询 + 提取串联需服务端编排（`meeting-transcribe/index.ts:77-86` 同进程 fetch 链式调用）。

**为什么用 Supabase SDK 直连做 CRUD 而不是自建 REST**：
- RLS 在数据库层强制 `user_id = auth.uid()`，无需应用层重复鉴权（`004_rls.sql` 全表策略）。
- 减少自建 API 的维护面，符合 SOW "单用户价值闭环"边界。

### 5.3 CLI —— 已用（研发层）

| CLI | 用途 | 在本项目的体现 |
|---|---|---|
| `git` | 版本控制、Trunk-based 分支、Conventional Commits | 3 个里程碑 commit（§8.1） |
| `npm` | 依赖、脚本（dev/build/test/lint/typecheck） | `package.json` scripts |
| `supabase` | `db:push` / `db:reset` 推送迁移、本地开发库 | `package.json:db:push/db:reset` |
| 飞书 CLI | （Skill `fde-mock-meeting-transcripts`）创建飞书文档作为 mock 数据源 | skill 定义，非应用代码 |

**为什么研发协作选 CLI 而非 API/MCP**：
- **issue tracker 用 markdown + git**（AGENTS.md）：issue 是 `.scratch/<feature>/` 下文件，天然走 git/file CLI，无需 API。这与 local-markdown 约定一致，可 diff、可 review、可离线。
- **确定性**：CLI 命令幂等可脚本化（CI 用 `npm ci` + `npm run test`，`.github/workflows/ci.yml`）。
- **低依赖**：无需额外起 server，研发链路最短。

### 5.4 MCP —— 选择依据（含"为何当前未引入"）

**当前不引入 MCP 的依据**：
1. **SOW §3 边界**：AI 不自主写外部系统，Agent 无需标准化工具协议去操作 Jira/飞书等。
2. **接入对象单一**：当前 Agent 接入的是本地文件（issue/docs）+ CLI + Supabase，这些用 CLI/SDK 已覆盖，MCP 的"统一工具发现"价值未显现。
3. **v1 交付密度**：5 个工作日 Sprint（SOW §8），优先打通 AI 业务闭环，不投入平台化工具层。

**未来引入 MCP 的触发条件（演进判断）**：
- 当 Agent 需要**同时操作多个异构外部系统**（如同时读写 Supabase + 飞书 + GitHub Issue）且这些操作要被多个 Agent 复用时，MCP 的标准化工具协议才有规模收益。
- 当要从"Agent 读 markdown issue"升级到"Agent 直接操作 issue 状态机"（如自动打 triage label）时，MCP server 封装这些操作比裸 CLI 更安全（可做权限收敛）。

**选择依据小结（三层优先级）**：
```
能用文件/CLI 解决 → 用 CLI（最轻、可 diff、可 review）
需密钥/服务端编排 → 用 Edge Function（API 范式，密钥隔离）
多 Agent 复用异构工具 → 才上 MCP（v1 未达此规模）
```

## 6. 安全与治理

### 6.1 身份认证

| 维度 | 实现 | 证据 |
|---|---|---|
| 认证方式 | Supabase Auth（邮箱密码 + Google OAuth） | `src/app/(auth)/` 登录/注册页；`src/app/auth/callback/route.ts` OAuth 回调 |

### 6.6 异常处理

**状态机兜底**（核心机制）：所有长任务走 `status` 枚举，任一环节失败/超时自动落 `failed` + `error_message`，前端展示重试。

```
[uploading]→[transcribing]→[analyzing]→[completed]
     任一环节失败/超时僵尸态(5min无更新) → [failed] →用户重试
```
证据：接口契约 §1.4；`meeting-transcribe/index.ts:162-167` markFailed；`meeting-extract/index.ts:124-133` catch 落 failed。

**错误码归一化**（接口契约 §0.3）：DashScope 实际返回 → 统一 `LLM_*` 错误码，带 `retryable` 标志。

| DashScope 返回 | 映射 | retryable | 实现 |
|---|---|---|---|
| HTTP 429 / Throttling | `LLM_RATE_LIMIT` | true | `_shared/supabase.ts:54-56` |
| 401/403 InvalidApiKey | `LLM_ERROR` | false | `_shared/supabase.ts:57-59` |
| 超时/网络不通 | `LLM_TIMEOUT` | true | — |
| 非法 JSON/内容截断 | `GENERATION_FAILED` | true（重试 1 次） | `meeting-extract/index.ts:64-77` 剥包裹+parse 容错 |

**重试策略**（接口契约 API-4）：服务端重试 1 次，仍失败落 `status=failed`。ASR 轮询最长 ~3 分钟（`meeting-transcribe/index.ts:135` maxAttempts=60 × 3s）。

**前端处理**：根据 `error.details.retryable` 决定是否显示"重试"按钮（接口契约 §0.3）。

### 6.7 人工兜底（核心设计哲学）
