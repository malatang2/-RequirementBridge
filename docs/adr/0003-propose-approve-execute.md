# Agent Proposal 须经人 Approve 方可执行（Propose-Approve-Execute 三段式）

v1 的底线是"AI 不执行任何落地动作"。v2 引入 Agent 执行引擎后，这条底线被放松——但放松的边界用一条新的、不可配置的底线补偿：**每一个 Agent Proposal 对外部系统的执行动作，必须经人 Approve 才能真正执行，无一例外**。这不是"AI 替你决定"，而是把"导出文件后人工搬运"升级为"AI 整理提议清单，你一键批准执行"。

## 边界一：审批永久强制，不可配置

不提供"关闭审批"开关，不提供"通过率达标的用户免审批"路径。代码里不存在"是否跳过审批"的分支。这是 v2 替代 v1"AI 不执行"原则的新的不可逆底线——既然放松了"不执行"，就必须用"必审批"补偿，否则信任崩塌。提供关闭开关必然因便利性滑坡而被关掉，等于无补偿地回到"AI 自主执行"。

## 边界二：批量批准降摩擦，不放松执行逻辑

降低审批摩擦的唯一手段是 UI 加速：提供"全选 → 批量批准"按钮，但每一批仍逐条计入审计、逐条可见，只是把 approve 的点击次数从 N 降到 1。不引入"半自动""白名单低风险动作自动执行""通过率阈值"等模糊概念——这些会重新打开滑动窗口。"半自动"若未来确有客户特例需求，作为单独 ADR 处理，不进 v2 通用基线。

## 边界三：MCP 只暴露 propose_*，不暴露 execute

MCP Server 暴露给外部 Agent 的工具集合**只包含 propose_* 类工具**（propose_create_jira / propose_split_tasks 等），**不暴露 execute 类工具**。执行动作只能通过 Web UI 的审批按钮触发，Agent 无法绕过审批直接执行。这从协议层面而非配置层面保证了边界一的不可绕过性。

## Considered Options

- **首月强制、之后按通过率开放免审批**：被否。"低风险动作"界定本身模糊，滑动风险高；通过率指标在免审批后会失真（提议质量无人监督）。
- **半自动（白名单低风险动作自动执行）**：被否。每接一个新第三方都要维护风险分级表，且"低风险"判定是模糊决策，会逐步侵蚀审批底线。
- **配置式自动批准规则**：被否。把"什么该自动"的决定权交给用户配置，等于变相审批开关，滑坡回"可关闭审批"。
- **MCP 暴露 execute_* 但加权限校验**：被否。权限校验是运行时检查，存在被绕过或误配置的风险；从协议层不暴露 execute 才是结构性保证。

## Consequences

- v1 的"AI 不执行"原则被这条 ADR 正式取代。代码库中 Approve 一词只出现在 Agent Proposal 上下文，与人发起的 Push（直接外发，走 `external_push_logs`）严格区分。
- 撤销窗口（24h）只对 Agent Proposal 执行有效；人发起的 Push 无撤销（与 v1 导出行为一致）。
