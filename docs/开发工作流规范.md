## 1. 软件工程开发流程（业界标准）

### 1.1 完整生命周期（SDLC）

主流软件工程生命周期分若干阶段，每阶段有明确入口、活动、产出、出口标准（Gate）：

```
需求 ─► 设计 ─► 开发 ─► 测试 ─► 发布 ─► 运维/迭代
 │       │       │       │       │       │
 │       │       │       │       │       └ 监控/告警/反馈→下一轮需求
 │       │       │       │       └ 灰度/全量/回滚
 │       │       │       └ 单测/集成/UAT/性能安全
 │       │       └ 编码/CR/联调
 │       └ 架构/数据/接口/UI
 └ 调研/PRD/评审
```

| 阶段 | 核心活动 | 关键产出 | 出口标准（Gate） |
|---|---|---|---|
| **需求 Requirements** | 调研、用户故事、PRD、范围界定 | PRD、SOW、需求清单、原型 | PRD 评审通过，范围边界确认 |
| **设计 Design** | 架构、数据库、API、UI 设计 | 架构图、DDL、接口契约、设计稿 | 设计评审通过（基线冻结） |
| **开发 Development** | 环境、编码、单测、代码评审、联调 | 源码、单测、技术文档 | 功能完成，单测通过，CR 通过 |
| **测试 Testing** | 用例、集成/系统/UAT、性能安全、Bug 修复 | 测试用例、报告、缺陷库 | 用例通过率达标，无 P0/P1 缺陷 |
| **发布 Release** | 预发布、上线 checklist、灰度/全量、回滚预案 | 生产环境、发布说明 | 预发布复测通过 |
| **运维 Operations** | 监控、反馈、缺陷修复、下轮规划 | 运行报告、迭代 backlog | SLA 达标 |

### 1.2 常见开发模型（按项目特点选择）

| 模型 | 特点 | 适用场景 |
|---|---|---|
| **瀑布 Waterfall** | 阶段串行，每阶段完整才进下一阶段 | 需求极度稳定、合同制大项目 |
| **迭代/增量 Iterative** | 分轮交付，每轮一个可工作增量 | 中大型产品，需求逐步明确 |
| **Scrum（敏捷）** | 固定 Sprint（1-4 周），每日站会，迭代评审 | 团队协作、需求变化快 |
| **看板 Kanban** | 持续流式，限制在制品（WIP），无固定周期 | 运维、持续维护、支持类工作 |
| **极限编程 XP** | TDD、结对、持续集成、小步重构 | 质量要求极高的核心系统 |

### 1.3 现代工程实践（贯穿各模型）

无论选哪种模型，成熟的工程团队通常都采用这些**横向实践**：

- **版本控制 + 分支策略**（Git Flow / Trunk-based / GitHub Flow）
- **代码评审（Code Review, CR / PR）**——合并前至少一人审查
- **持续集成 CI**——每次提交自动跑 lint + 测试 + 构建
- **自动化测试金字塔**——单测多、集成少、端到端精简
- **环境分层**——本地 / 开发 / 预发布 / 生产
- **基础设施即代码 IaC**——数据库迁移、配置用代码版本化管理
- **可观测性**——日志、指标、链路追踪
- **小步提交 + 频繁集成**——避免长生命周期分支

> 核心思想：**把质量左移（shift-left）**——问题越早发现（设计>开发>测试>上线），修复成本越低。

## 2. 本项目特点分析（决定工作流选型）

| 维度 | 现状 | 对工作流的影响 |
|---|---|---|
| **团队规模** | 小团队（PM + 研发负责人 + 后端 + 前端，可能更少） | 不需要重型 Scrum 角色（无 SM/PO 分离）；CR 可轻量 |
| **产品形态** | v1 单用户、Web 应用 | 无多人并发/权限复杂度；RLS 是安全核心 |
| **交付周期** | **5 个工作日 Sprint**（Day 2-6） | 不能用瀑布；必须短迭代、高频集成 |
| **技术栈** | Next.js(App Router, TS) + Supabase + OpenAI + Vercel | 全栈一体、Serverless；CI/CD 由 Vercel 承载；DB 用迁移 |
| **AI 依赖** | 三模块核心是 OpenAI（Whisper+GPT-4o） | **AI 产出质量是头等风险**——需要专门的"评测门禁"，普通功能测试覆盖不了 |
| **设计状态** | 已评审冻结（数据模型/接口/UI 三份基线） | 开发有明确依据，应"按图施工"，变更走流程 |
| **质量要求** | SOW §6.2 有 12 项准确度门槛（部分程序化、部分人工） | 需把验收门槛前移为开发期的自动化检查 |
| **合规风险** | 音频/反馈送 OpenAI（评审已决议 B1 口径） | 合规口径必须落到代码（脱敏/提示/保留期），不能漂移 |
| **部署** | Vercel 预览 + 生产 | 天然支持预发布（Preview Deployment）做 UAT |

### 选型结论

> **本项目采用：轻量敏捷（短 Sprint）+ Trunk-based 分支 + 强制 CR + CI 自动门禁 + AI 评测门禁 + Vercel 预发布验收。**

理由：
- **不用瀑布**：5 天周期，瀑布的串行 Gate 会来不及。
- **不用重型 Scrum**：人少，每日站会可保留但角色简化。
- **不用 Git Flow 的 release/hotfix 长分支**：小项目维护成本高；用 **Trunk-based + 短特性分支 + PR**，配合 Vercel Preview 做验证。
- **必须加 AI 评测门禁**：这是本项目区别于普通 CRUD 的关键——OpenAI 产出的"准不准"用评测集把关，而不是靠人工点点点。

## 3. 订制开发工作流（本项目适用）

### 3.1 总览图

```
┌─────────────────────────────────────────────────────────────────┐
│  设计基线（已冻结）                                                │
└────────────────────────────┬────────────────────────────────────┘
                             ▼
   ┌──────────────────────────────────────────────────────────┐
   │  每日循环（Day 2-6）                                        │
   │                                                            │
   │  晨会(10min) ─► 开发 ─► 提交 ─► CI 门禁 ─► CR ─► 合并       │
   │                  │                          │              │
   │                  └─► AI 链路额外走"评测门禁" ◄┘              │
   │                                                            │
   │  EOD：当日任务达 DoD（排期 §3），更新进度                    │
   └────────────────────────────┬────────────────────────────────┘
                                ▼
   ┌──────────────────────────────────────────────────────────┐
   │  Day 6：集成联调 + 准确度评测 + Demo（CP5）                  │
   └────────────────────────────┬────────────────────────────────┘
                                ▼
          预发布（Vercel Preview）UAT ─► 修复 ─► 生产发布
```

### 3.2 分支策略（Trunk-based + 短特性分支）

| 分支 | 用途 | 生命周期 | 命名 |
|---|---|---|---|
| `main` | 生产分支，始终可部署 | 永久 | `main` |
| `feature/*` | 开发一个任务/模块 | 1-2 天，尽快合并 | `feature/T0.2-supabase-schema` |
| `fix/*` | 修 Bug | 短 | `fix/meeting-status-polling` |

**规则**：
- **不直接 push `main`**；所有改动经 PR 合并。
- 特性分支**最多存活 2 天**；超期拆分。
- 合并前必须：CI 绿 + 至少 1 人 CR 批准。
- 合并方式：**Squash merge**（保持 main 历史线性）。
- 合并后**删除特性分支**。

> 为何不用 Git Flow：v1 单线发布、无多版本并行，Git Flow 的 `develop/release/hotfix` 是负担。Trunk-based 让"main 永远可部署"。

### 3.3 提交规范（Conventional Commits）

```
<type>(<scope>): <subject>

type:   feat | fix | docs | style | refactor | test | chore | perf | ci
scope:  meeting | api | feedback | auth | db | ui | infra（对应模块/任务）
subject: 简述，动词开头
```

示例：
- `feat(meeting): 实现音频上传与 Whisper 转录链路 (#T1.1)`
- `fix(db): 修正 feedback_topics 频次触发器 (#T0.2)`
- `test(api): 增加 OpenAPI YAML 合法性单测 (#T2.2)`

**规则**：提交信息关联任务 ID（`#T1.1`），便于追溯 DoD。

### 3.4 代码评审（CR / PR）

| 项 | 要求 |
|---|---|
| 触发 | 所有合并到 `main` 的改动 |
| 审查人 | 至少 1 人；跨模块改动需研发负责人审查；安全相关（RLS/鉴权/密钥）必须由研发负责人或安全角色审查 |
| 检查清单 | ①符合设计基线（数据模型/接口契约）②无硬编码密钥 ③RLS 策略正确 ④错误处理完整 ⑤关键路径有测试 ⑥AI 产出有评测 |
| 时效 | PR 提出 4 小时内有人响应；不阻塞过夜 |
| 规模 | 单 PR < 400 行改动（超出拆分） |

**CR 重点（本项目专属）**：
- 任何写入 `main` 的 Edge Function：检查 OpenAI key 是否仅在服务端、是否做了错误捕获与 status 落库。
- 任何 RLS 策略改动：必须双人确认（防越权是安全红线）。
- 任何 Prompt 改动：必须同步更新评测集预期，标注"可能影响准确度指标"。

### 3.5 测试策略（测试金字塔，适配 AI 产品）

```
            /\
           /e2e\        ← 端到端（Day 6 联调，少量关键链路）
          /------\
         / 集成测试 \     ← Edge Function + DB + Storage
        /------------\
       /   单元测试    \   ← 纯函数、工具、YAML 校验、Prompt 后处理
      /----------------\
     /  AI 评测门禁 ★   \  ← 本项目特有：用评测集验证 AI 产出质量
    /--------------------\
```

| 层级 | 范围 | 工具 | 何时跑 |
|---|---|---|---|
| **单测** | 工具函数、YAML 解析校验、camelCase 扫描、Prompt 后处理逻辑 | Vitest | 每次提交（CI） |
| **集成测试** | Edge Function 端到端（mock OpenAI）、RLS 隔离验证（A/B 账号） | Vitest + Supabase 本地 | 合并前 + Day 6 |
| **AI 评测** | 用固定评测集跑真实 OpenAI，对照 12 项准确度门槛 | 自建评测脚本 | **每次 Prompt/链路改动 + Day 6** |
| **端到端** | 三模块核心链路（上传→产出→导出） | 手动 + Playwright（可选） | Day 6 联调 |

**AI 评测门禁（本项目核心，详见 §4）**：这是普通功能测试无法替代的——AI 输出是非确定性的，必须用"固定输入 + 预期质量门槛"来把关。

### 3.6 数据库迁移（基础设施即代码）

- **所有 schema 改动走迁移文件**，不手改 Supabase 控制台。
- 迁移文件按数据模型 §9 顺序编号：`supabase/migrations/001_enums.sql` … `006_storage.sql`。
- 命名：`<序号>_<描述>.sql`，如 `007_add_requirement_status.sql`。
- 迁移**只增不改**（已应用的迁移不修改，新需求加新文件）。
- RLS 策略改动走迁移 + CR 双人确认。

### 3.7 环境分层

| 环境 | 用途 | 数据 | 访问 |
|---|---|---|---|
| **本地** | 开发调试 | Supabase 本地 + OpenAI 测试 key | 开发者 |
| **预览（Vercel Preview）** | PR 自动部署，UAT/评审 | 独立 Supabase 项目（测试数据） | 团队 + PM |
| **生产** | 线上 | 生产 Supabase | 终端用户 |

- 每个 PR 自动生成 Vercel Preview URL，PM/前端可直接验收。
- **OpenAI key 分环境**：本地用测试 key（限额），生产用正式 key。
- 生产 Supabase 与测试 Supabase **物理隔离**，绝不共用。

### 3.8 每日节奏（轻量敏捷）

| 时间 | 活动 | 时长 |
|---|---|---|
| 09:30 | 晨会：昨日完成 / 今日计划 / 阻塞 | 10 min |
| 白天 | 开发 + 提交 + CI + CR | — |
| EOD | 当日任务达 DoD；更新排期进度；Preview 可验收 | 5 min |

> **不做**：冗长的迭代计划会、故事点估算扑克（5 天 Sprint 用不上）；保留"每日同步 + DoD 验收"即可。

## 4. AI 评测门禁（本项目特有，重点）

> 三模块的核心价值都依赖 OpenAI 产出质量。功能测试只能验证"接口通不通"，**验证不了"AI 准不准"**。因此设立独立的 AI 评测门禁。

### 4.1 评测集（Golden Set）

每模块准备一份**固定评测集**，纳入版本库（`tests/eval/`），作为质量基线：

| 模块 | 评测集 | 规模 | 内容 |
|---|---|---|---|
| 会议 | `meeting_eval.json` | 10-20 条 | 会议文本 + 预期分类/负责人/优先级标注 |
| API | `api_eval.json` | 10-20 条 | 业务需求 + 人工判分要点 |
| 反馈 | `feedback_eval.json` | 10-20 条 | 反馈列表 + 预期聚类/情感 |

### 4.2 门槛与门禁动作

对照 SOW §6.2 / 排期 §4 的 12 项指标：

| 类型 | 指标示例 | 门禁动作 |
|---|---|---|
| **程序化**（必须达标） | OpenAPI 合法率 100%、错误码 100%、频次 100%、camelCase ≥95%、引用追溯 ≥90% | **不达标 = CI 失败，PR 不允许合并** |
| **人工**（抽检 5 分制） | 分类准确率 ≥80%、聚类合理度 ≥4、语义相关度 ≥4 | 人工跑评测脚本打分，记录到 PR；连续 3 批不达标须回查 Prompt |

### 4.3 触发时机

- **每次 Prompt 改动**：必须跑对应模块评测。
- **每次 AI 链路改动**（Edge Function 逻辑）：必须跑评测。
- **Day 6（CP5）**：三模块全量评测，达标方可进入 Demo/发布。
- **生产发布前**：预发布环境复跑评测集，确认无回归。

> 评测脚本消费真实 OpenAI（有成本），因此**不在每次 CI 跑**，而在"Prompt/链路改动时手动触发 + 里程碑全量跑"。

### 4.4 评测 → 修复闭环

```
跑评测 ─► 达标？─是─► 通过门禁
            │
            否
            ▼
        记录不达标项 ─► 迭代 Prompt / 修后处理逻辑 ─► 重跑 ─►（循环至达标）
```

## 5. 门禁汇总（Definition of Done，逐层）

> "一个任务怎样算完成？"——本节给出本项目分层 DoD，避免"代码写完 ≠ 任务完成"。

### 5.1 任务级 DoD（每个 T 任务）

- [ ] 代码符合设计基线（数据模型/接口契约/UI 线框）
- [ ] 通过 lint + 类型检查（TypeScript strict）
- [ ] 关键逻辑有单测且通过
- [ ] AI 链路任务：跑过评测且达标（§4）
- [ ] PR 经至少 1 人 CR 批准
- [ ] 关联任务 ID，DoD 描述的能力可验证

### 5.2 模块级 DoD（M1/M2/M3）

- [ ] 核心链路端到端可走通（输入→AI→展示→导出）
- [ ] status 状态机正常流转（含 failed 重试）
- [ ] RLS 验证通过（仅本人可见）
- [ ] 模块准确度门槛全项达标
- [ ] Vercel Preview 可供 PM 验收

### 5.3 Sprint 级 DoD（Day 6，CP5）

- [ ] 三模块在统一 Dashboard 下连贯操作
- [ ] 三模块各一核心链路可演示
- [ ] 全量准确度评测达标并留档
- [ ] 无 P0 缺陷；P1 缺陷有明确处理计划
- [ ] 埋点（PostHog）就位

### 5.4 发布级 DoD（生产上线）

- [ ] 预发布环境功能 + 准确度复测通过
- [ ] 上线 checklist 全项 ✓（环境变量、key、域名、RLS、Storage 策略）
- [ ] 合规口径已落地代码（B1 决议：脱敏/提示/保留期）
- [ ] 回滚预案就绪（Vercel 即时回滚）
- [ ] 监控/告警就位（PostHog + status=failed 落库可查）

## 6. 变更管理（基线已冻结，如何改）

设计基线（数据模型/接口契约/UI）已通过 CP0 冻结。开发中如需变更：

| 变更类型 | 流程 | 示例 |
|---|---|---|
| **小改**（实现细节、补字段、调 UI） | PR 内说明，CR 时知会，更新文档 | 加一个索引、调按钮位置 |
| **中改**（改接口签名、加表/字段、改状态机） | 提变更说明，研发负责人确认，更新基线文档版本 | Edge Function 增返回字段 |
| **大改**（动范围、动数据模型核心、动合规口径） | 走 SOW 变更流程，重排 §3/§5，必要时重开评审 | 新增模块、改 RLS 边界 |

**原则**：文档与代码同步——**改了代码就要改对应基线文档**，否则下次评审/交接会失真。

## 7. 风险与工程对策（本项目专属）

| 风险 | 工程对策 |
|---|---|
| AI 产出不准 | AI 评测门禁（§4）；Prompt 改动必跑评测 |
| OpenAI 超时/限流/成本 | 服务端重试 1 次 + status=failed；key 分环境限额；用量日志 |
| RLS 越权（安全红线） | RLS 改动双人 CR；A/B 账号集成测试 |
| 5 天周期紧 | Trunk-based 高频集成；AI 链路优先于前端；前端可降级 |
| Edge Function 单次执行时长 | B3 决议：超时降级轮询；音频直传 Storage |
| 合规口径漂移 | 合规逻辑集中在 Edge Function 入口；CR 专项检查 |
| 长分支冲突 | 特性分支 ≤2 天；每日合并 |

## 8. 工具链一览

| 环节 | 工具 |
|---|---|
| 版本控制 | Git + GitHub |
| 分支/CR | GitHub PR + Squash merge |
| CI | GitHub Actions（lint + 类型 + 单测 + 构建） |
| 前端框架 | Next.js(App Router) + TypeScript + Tailwind + shadcn/ui |
