## 一、v1 开发内容总结

### 1.1 产品定位

RequirementBridge（需求桥）：帮助产品经理把**散点式的会议决策与多渠道用户反馈**，用 AI 一次性转化为**结构化的产品需求**与**可执行的 OpenAPI 技术定义**。

三大模块 + 单用户 + 项目隔离 + 通义千问（DashScope）。

### 1.2 交付物清单

| 类别 | 内容 | 数量/规模 |
|---|---|---|
| **源代码** | Next.js 15 + TypeScript 前端 + Supabase Edge Function | 69 个源文件 |
| **Edge Functions** | meeting-extract / meeting-transcribe / api-generate / feedback-analyze / feedback-gen-requirement / b5-health-check | 6 个（已部署） |
| **数据库迁移** | 枚举/表/索引/RLS/触发器/Storage | 6 个 SQL 文件 |

### 1.3 三大模块功能

#### 模块一·会议纪要（`/dashboard/meetings`）
- 音频上传（mp3/wav/m4a ≤50MB）+ 文本粘贴两种输入
- fun-asr/Paraformer 转录 → Qwen-Max 结构化提取（决策/待办/需求/问题）
- 整体摘要 + 每条原文引用（可追溯）
- 条目可编辑/删除/改优先级/改负责人/手动新增
- 导出 Markdown / CSV / 复制

#### 模块二·API 设计器（`/dashboard/api-designer`）
- 业务需求（必填）+ API 规范上下文（选填）
- Qwen-Max 生成 OpenAPI 3.0 YAML（camelCase + 400/401/404/500 + schemas）
- 代码视图（可编辑 + js-yaml 实时校验）+ 可视化视图（Swagger 卡片）
- 版本保存 / 历史 / 重新生成
- 导出 YAML / JSON / 复制

#### 模块三·反馈洞察（`/dashboard/feedback`）
- 粘贴反馈（每行一条）
- Qwen-Plus 主题聚类 + 情感 + 频次 + 优先级 + 样本
- 统计卡 + Recharts 条形图（频次降序）+ 情感饼图
- 主题编辑 / 合并 / 删除
- 勾选主题生成需求草稿 → 草稿列表页

#### 通用与平台
- 邮箱密码登录 + 登录态守卫（middleware）
- Dashboard：项目选择器 + 三模块导航 + 项目 CRUD（按项目隔离）
- 全表 RLS（user_id = auth.uid()）
- status 状态机 + 轮询 hook（含超时僵尸态检测）
- PostHog 埋点（可选启用，无 key 降级）

## 二、开发流程梳理

### 2.1 流程总览

```
需求阶段 ─► 设计阶段 ─► 开发（Day2-6 Sprint）─► 验收 ─► 上线
  ✅          ✅            ✅                ✅      ✅
```

采用 **轻量敏捷 + Trunk-based + TDD（mattpocock skills）+ AI 评测门禁** 的工程模式。

### 2.2 各阶段实际执行

| 阶段 | 周期 | 关键活动 | 关键产物 |
|---|---|---|---|
| **需求** | Day 1 | 调研、PRD、SOW、排期 | 需求清单、SOW、排期文档 |
| **设计** | Day 2 上午 | CP0 评审（数据模型/接口/UI）+ 冻结基线 | DDL + RLS、接口契约、UI 线框、评审清单 |
| **开发** | Day 2-6 | TDD 纯逻辑 + Edge Function + 页面 | 三模块全链路代码 |
| **验收** | Day 6 | AI 评测 + 联调 + 12 测试用例 | 评测脚本、验收报告、上线 checklist |
| **上线** | Day 6+ | Vercel 部署 + 环境配置 | 生产环境运行中 |

### 2.3 关键工程实践（值得保留）

1. **设计前置（CP0 冻结）**：数据模型/接口/UI 在开发前评审冻结，避免"边开发边改表"的隐性返工——这是 v1 能 5 天完成三模块的关键。
2. **TDD 纯函数 seam**：把可测的业务逻辑（校验/解析/统计）抽成纯函数，与 DB/EF 调用分离。150 个单测覆盖核心逻辑，重构时不破。
3. **AI 评测门禁**：用固定评测集 + 程序化校验把关 AI 产出质量（非人工目测）。**实际发现了 2 个质量问题并修复**（API 错误码缺失、YAML 清理健壮性）。
4. **RLS 双重验证**：触发器保证频次一致性 + integration-check 脚本验证越权拦截。
5. **错误码归一化**：DashScope 错误码 → 统一 LLM_* 错误码，前端 retryable 判断不漂移。

### 2.4 关键决策点（影响架构）

| 决策 | 选项 | 结论 | 影响 |
|---|---|---|---|
| AI 服务选型 | OpenAI vs 通义千问 | **通义千问**（CP0） | 化解合规（不出境）+ 成本两大阻断 |
| 网络方案 | Edge Function vs 阿里云 FC | **Edge Function**（B5 实测 P50≈1.8s） | 无需迁 FC，但保留 LLMProvider 接口 |
| 数据合规 | 强脱敏 vs 提示 | **国内不出境 + 提示不强脱敏**（B8） | v1 基线达成 |
| 频次触发器 | 原实现 vs 修复 | **修复跨主题 BUG**（#1a②） | 频次 100% 一致 |

## 五、最终结论

### v1 达成的目标
- ✅ 三大模块"输入 → AI 结构化（通义千问）→ 人校对 → 导出"全链路就绪
- ✅ 准确度门槛达标（5/5 评测 + 12 测试用例）
- ✅ 安全隔离有效（RLS 10/10）
- ✅ 生产环境运行中（Vercel）
- ✅ 业务有效解决率 100%

### v1 的技术债性质
**无阻断性技术债**。遗留问题分两类：
- **配置/部署类**（K-2/K-3/D-1/D-3）：配一下就好，非代码问题
- **代码优化类**（TD-1~TD-6）：v1 可接受的权衡，不影响功能正确性，v2 逐步偿还

### 关键经验
1. **设计前置 + TDD + AI 评测门禁** 是 v1 能高质量快速交付的三支柱
2. **CP0 评审的模型迁移决策**（OpenAI→通义千问）一举化解两大阻断，是项目关键转折
3. **评测脚本真实发现了质量问题**——证明"程序化校验"比人工目测更可靠
