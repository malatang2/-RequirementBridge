## 1. 产品定位（一句话）

帮助产品经理把**散点式的用户反馈与会议决策**，高效转化为**结构化的产品需求**，并进一步精准转化为**可执行的技术需求（API 草稿）**，降低产研沟通成本与返工。

> 价值锚点：会议决策不落地、反馈难聚类、需求转接口靠反复对齐——这三件事由 AI 一次性结构化。

## 2. 客户与使用者

| # | 角色 | 描述 | 核心诉求 | 主要使用模块 |
|---|---|---|---|---|
| 1 | 产品经理（PM，主用户） | 中小团队 / 独立产品负责人，常需独自消化会议与多渠道反馈 | 快速把会议与反馈变成结构化需求与待办，少做重复整理 | 模块一、二、三（全量） |
| 2 | 研发 / 后端工程师（协作者） | 接收 PM 需求并实现 | 拿到清晰、可执行、低歧义的接口定义，减少返工 | 模块二（API 草稿评审/编辑） |
| 3 | 小团队负责人（决策者/买单者） | 关注产研效率和需求质量 | 可量化的沟通与返工成本下降 | 看板/导出报告 |
| 4 | 终端用户（间接） | 产品最终使用者 | 其反馈被听见并转化为改进 | 其反馈作为模块三输入 |

> 注：v1 数据模型按"单用户 + 项目"组织（Supabase RLS 限定本人数据），**团队级多人协作不在 v1 范围**（见 §5）。

## 3. 当前业务问题（AS-IS 痛点）

### 3.1 会议侧
- 会议录音/笔记散落在不同工具，**关键决策易遗漏**。
- 纪要靠人工整理，**耗时且标准不一**；待办（Action Item）常常**无人跟进或负责人不明**。
- 会议结论到"可执行需求"之间**缺少结构化沉淀**。

### 3.2 需求转技术侧
- PM 写自然语言 PRD，研发**凭理解手写接口**，理解偏差在联调阶段才暴露 → **返工**。
- 缺少统一的 API 规范载体，**接口定义反复口头/文档对齐**。

### 3.3 反馈侧
- 多渠道反馈（客服、NPS、社群）**分散**，逐条人工阅读**成本高**。
- 聚类、频次、情感**靠人工估算**，优先级**主观**，难以横向比较。

### 3.4 横向
- 三个环节彼此割裂，**没有从"会议决策 → 需求 → 接口"的贯通链路**，数据需人工搬运。

## 4. 范围内（In Scope，v1）

### 4.1 模块一：智能会议纪要与任务提取（`/dashboard/meetings`）
- 输入：上传音频（mp3/wav/m4a，≤50MB）或粘贴文本。
- AI 流程：fun-asr/Paraformer 转录 → Qwen-Max 结构化提取【决策 / 待办 / 需求 / 遗留问题】，含负责人、优先级、原文引用、整体摘要。
- 结果：按类型分组展示，**全条目可编辑/删除/改优先级/改负责人**，支持手动新增。
- 导出：Markdown、CSV、复制到剪贴板。

### 4.2 模块二：业务需求 → API 草稿生成（`/dashboard/api-designer`）
- 输入：业务需求描述（必填）+ API 规范上下文（选填）。
- AI 流程：Qwen-Max 生成 **OpenAPI 3.0 YAML**（路径/方法/参数/响应/Schemas/认证/错误码，camelCase）。
- 结果：代码视图（高亮 + 可编辑 + 实时 YAML 校验）与可视化视图（Swagger 风格卡片）；支持重新生成、版本保存、版本历史。
- 导出：YAML、JSON（OpenAPI）、复制。

### 4.3 模块三：智能用户反馈洞察（`/dashboard/feedback`）
- 输入：粘贴文本（每条换行）或上传 CSV/TXT（CSV 需指定反馈列）。
- AI 流程：Qwen-Plus 做**主题聚类 / 命名 / 摘要 / 频次 / 情感 / 优先级建议 / 样本反馈**。
- 结果：统计卡片（总数/主题数/高优数/负面占比）、横向条形图、情感饼图、可折叠主题卡（可编辑/合并/删除）。
- 衍生：勾选主题 → **生成需求草稿**（可编辑、可导出）。
- 导出：Markdown 报告、CSV 主题、PNG 图表、复制。

### 4.4 通用与平台
- Landing Page、邮箱/Google OAuth 登录、Dashboard 布局（项目选择器 + 三模块导航 + 设置/登出）、项目 CRUD、Light/Dark、响应式。
- 埋点 PostHog（自定义事件 + pageview）、流量 GA4、SEO（meta / sitemap / robots / 预留百度与 GSC 验证）。
- 技术底座：Next.js(App Router, TS) + Tailwind + shadcn/ui + Supabase(Postgres/Auth/Storage/Edge Functions) + **阿里云百炼/DashScope（通义千问 Qwen + Paraformer/fun-asr）** + Vercel，支付预留 Stripe。
  > 【CP0 决议 2026-07-29】AI 服务由原 OpenAI 迁移至**通义千问（DashScope）**：文本用 Qwen-Max（生成类）/Qwen-Plus（聚类类），语音转写用 fun-asr（备选 Paraformer-v2）。一举化解 Q1 合规（数据不出境）与 Q9 成本两大阻断项；DashScope 提供 OpenAI 兼容接口，迁移成本可控。详见《设计评审清单 §6》。

## 5. 范围外（Out of Scope）—— 明确"不做什么"

> 以下为 **v1 明确不做**，需在评审中确认是否纳入 v2 路线图。

1. **不做团队级多人协作**：v1 以"单用户 + 项目"为边界（RLS 限定本人数据），不支持成员角色、共享编辑、评论 @、权限分级。
2. **不做与第三方系统的实时双向集成**：不直连 Jira / 飞书 / 钉钉 / Linear / Swagger / Postman；产出仅通过**导出文件（MD/CSV/YAML/JSON/PNG）**和剪贴板外溢。
3. **不做 API 草稿的实时预览联调 / Mock Server**：仅生成与展示 OpenAPI 定义，不提供请求调试、Mock 返回、代码生成（SDK）。
4. **不做反馈的渠道直采**：不直接对接客服系统/NPS 平台/应用商店评论 API，需用户**手动粘贴或上传文件**。
5. **不做事由 AI 自主执行任务**（无 Agent 自主写入外部系统）：AI 仅做"转录 / 提取 / 生成 / 聚类"，所有落地动作由人确认与导出。
6. **不做会议纪要 → API 草稿 → 反馈洞察的自动串联流水线**：三大模块在 v1 相互独立，不自动把"会议需求"喂给"API 设计器"或把"反馈主题"喂给需求池（该串联为待确认项，见 §9）。
7. **不做音视频多模态分析与说话人分离（Diarization）**：v1 仅做语音转文本与文本结构化，不区分发言人、不分析语气情绪。
8. **不在 v1 做私有化/本地大模型部署**：统一走**阿里云百炼/DashScope（通义千问）**云托管 API（数据合规见 §7、§9）。【CP0 决议：由 OpenAI 迁移至 DashScope，国内区域不出境】

## 8. 项目假设

1. 用户具备基本的产品/技术语境，能判断 AI 产出的准确性并完成校对。
2. 通义千问/DashScope API（Qwen + fun-asr/Paraformer）可用性、延迟、价格在可接受范围；key 由部署方提供（百炼控制台开通）。【CP0：由 OpenAI 迁移】
3. 单用户场景足以验证价值，**团队协作非 MVP 必需**。
4. 各模块的输出**以"人确认 + 导出"为终点**，企业系统对接以离线文件为主。
5. 输入语料以**中文**为主，少量英文；Qwen/fun-asr 对中文会议与反馈的理解质量达标。
6. 用户接受将相关数据上传至 Supabase 与阿里云百炼/DashScope（国内区域）处理。
7. 三大模块在 v1 **相互独立**，不强制端到端串联。

## 10. 初步业务指标（北极星 + 分层）

### 北极星指标
- **有效结构化产出数**（会议条目 + API 草稿 + 反馈主题，且未被用户大幅改写）——衡量"AI 真正替代了多少人工整理"。

### 获取与激活
- 注册 → 首次会议分析完成 → 首次 API 草稿生成 → 首次反馈分析 的**漏斗转化率**。
- 首次分析完成耗时（从创建到 completed）。

### 使用与价值（分模块）
- **会议**：人均周分析会议数；条目**未编辑率**（`is_edited=false`，越高说明 AI 越准）；待办有负责人的比例。
- **API**：草稿生成后研发**采纳率 / 平均编辑距离**；重新生成次数；版本保存数。
- **反馈**：聚类覆盖率（被归入主题的反馈 / 总反馈）；高优主题命中率（事后是否进入排期）。

### 质量与效率
- 单次会议纪要产出时长（对标人工基线）。
- 接口联调阶段返工率（需研发表单/访谈获取，定性为主）。

### 留存与商业
- W4 留存、模块级周活（WAU/模块）。
- 付费转化（Stripe 上线后）、AI 调用毛利率。

### 埋点 → 指标对应（已在源需求定义）
PostHog 事件（`meeting_created / analysis_completed / item_edited`、`api_generation_completed / api_spec_edited / api_version_saved`、`analysis_completed / topic_merged / requirement_draft_generated` 等）可直接支撑上述"使用与价值"层指标。
