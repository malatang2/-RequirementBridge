## 0. v1 → v2 的根本转变

| 维度 | v1 现状 | v2 目标 |
|---|---|---|
| **产品形态** | 三个独立 AI 提取器（会议 / API / 反馈），需求模块是只读汇总页 | **以需求为枢纽的产研流转中枢**：信号降噪 → 人工确认 → 落地执行 |
| **数据流向** | 三模块各自闭环；需求草稿仅来自 `feedback_topic` 一种来源 | 三路信号（会议 / 反馈 / 手工）汇入统一需求池；需求向下驱动 API 设计与外发 |
| **AI 边界** | "AI 仅生成、不执行" | **"AI 提议、人审批、才执行"**（Propose-Approve-Execute 三段式，Phase 3.4） |
| **配置方式** | LLM Key/模型写死在环境变量，无 UI | 用户配置页（模型选择 / Key 加密存储 / Provider 切换） |
| **外溢方式** | 仅文件导出（MD/CSV/YAML/JSON/PNG） | 文件导出 + 第三方系统回写（Jira/飞书/Linear/Swagger）+ Agent 执行引擎 |
| **可观测** | llm_usage 留痕但无可视化；无 Dark 模式；Landing 占位 | 用量看板（usage_daily 聚合）+ Dark 模式 + Landing 完整化 + 大音频续查强化 |
| **技术债** | EF 内 LLM 调用重复、转写多一跳 fetch、聚类逐条 update、EF 无单测 | LLM 入口统一、转录提取共享函数、聚类批量 update、EF 单测 + swagger-parser |
| **北极星** | 有效结构化产出数 | **有效确认需求数** + 需求流转完成率 + 跨模块跳板使用率 |

v2 的核心叙事（已与用户确认）：**把"需求"从只读汇总页升级为唯一中枢**，让一条需求从「会议/反馈产生 → 人工确认 → 进入需求池 → 转 API / 外发到 Jira」这条路径上的每一个跳板都被打通且可度量。

**架构原则（沿用 v1）**：
1. 前后端不分离的 Next.js 全栈单体，业务逻辑集中在 `src/lib/**` 纯函数 seam，便于测试。
2. AI 任务走 Edge Function（service_role 直写 DB）+ 前端轮询 status 字段。
3. 全表 RLS，策略统一 `user_id = auth.uid()`；单用户边界（团队协作留 v3）。
4. 校验全手写纯函数（无 zod），返回判别联合 `{ ok, error?, value? }`。

## 2. 数据模型变更（跨 Phase 全景）

这是 v2 改动最集中、最需要前置设计的部分。**采用增量演进**：一个迁移加字段，不动 v1 既有结构，保证可回滚。

### 2.1 迁移文件规划

```
supabase/migrations/
├── 001_enums.sql ~ 006_storage.sql          # v1 既有（不动）
├── 007_v2_requirement_hub.sql               # Phase 1：需求模块升级（核心）
├── 008_v2_feedback_source.sql               # Phase 1：反馈来源追溯 + 会议转入
├── 009_v2_api_origin.sql                    # Phase 2：API 草稿来源 + 自定义
```

### 2.3 枚举变更

```sql
-- 007_v2_requirement_hub.sql
create type requirement_lifecycle as enum (
  'draft',       -- 草稿（AI 生成或转入后默认）
  'confirmed',   -- 已确认纳入需求池（人工把关）
  'in_progress', -- 进行中（已带入 API 设计 / 开发中）
  'delivered',   -- 已交付
  'parked'       -- 搁置
);

-- source_type 从 text 升级（不破坏老数据）：
--   v1: 'feedback_topic' / 'manual'
--   v2: + 'meeting_item'
-- 保持 text 类型，应用层约束取值集合（避免 alter type 重写全表）

-- P2: meeting_item_category 增加 'user_feedback'
--   alter type meeting_item_category add value 'user_feedback';
--   ⚠️ MVP 阶段（P1）不扩，复用 issue + transferred_to_feedback 标记

-- P2: api_draft_origin
create type api_draft_origin as enum ('ai_generated', 'manual', 'imported');
```

### 2.4 触发器与约束

沿用 v1 的触发器模式（`fn_set_updated_at` / `fn_mark_*_edited`），新增：

- **`trg_requirement_lifecycle_sync`**：需求 `lifecycle` 改为 `confirmed` 时，写埋点审计（或由应用层 `track()` 处理，不滥用触发器）。
- **`check_requirement_source_consistency`**：`source_type='meeting_item'` 时要求 `source_meeting_item_id is not null`；`source_type='feedback_topic'` 时要求 `source_topic_id is not null`。
- **修复 v1 K-1**：`alter table projects add constraint projects_name_not_blank check (length(btrim(name)) > 0);`（DB 层兜底，前端已拦截）。

### 2.5 RLS 策略（新表照抄模板）

所有新表/新字段遵循 v1 的 RLS 统一策略 `user_id = auth.uid()`，四条 policy（select/insert/update/delete）。`external_push_logs`、`agent_execution_logs` 只需 select + insert（审计表，不可改删）。

## 3. 模块边界与跨模块数据流

这是 v2 最关键的设计——明确每个模块"负责什么、不负责什么"，避免耦合。

### 3.1 黄金路径（端到端数据流）

```
[会议模块]                     [反馈模块]                  [需求模块]              [API 模块]            [外部系统]
音频/文本                      反馈池（聚类）               统一需求池               API 草稿              Jira/飞书/...
   │  meeting-extract            ▲                              │                       │                    ▲
   ├─ decision/todo  ──留会议──┘  │                              │                       │                    │
   ├─ requirement  ──(P1)转入──►  │  feedback-analyze            │                       │                    │
   └─ user_feedback ──(P1)转入──► │  (合并会议来源+渠道+批量导入) │                       │                    │
                                  │  主题/情感/频次/优先级         │                       │                    │
                                  │                              │                       │                    │
                                  └──(P1)勾选主题→确认关卡──────►  │  feedback-gen-req     │                    │
                                                                 ├─ priority/lifecycle   │                    │
                                                                 ├─ source 追溯           │                    │
                                                                 │                       │                    │
                                                                 └──(P1)一键带入────────► │  api-generate       │                    │
                                                                                          │                    │
                                                                                          └──(P3)外发回写──────►┘
                                                                                          └──(P3.4)Agent提议──►┘
                                                                                              (人审批→执行)
```

**关键设计决策（用户已拍板）**：
- 会议条目**不直接变需求**，而是先进反馈池参与聚类 → 人从聚类后主题筛选 → 纳入需求。这保证"信号经过降噪"。
- 会议条目转入反馈后，**原会议记录保留不动**（仅标记 `transferred_to_feedback=true`），形成可追溯链路。

### 3.2 各模块职责矩阵

| 模块 | v1 职责 | v2 新增职责 | 明确不做 |
|---|---|---|---|
| 会议 | 音频转写 + AI 提取四类条目 + 编辑/导出 | 条目"一键转入反馈"按钮；`user_feedback` 类目（P2） | 不直接生成需求（走反馈池中转） |
| 反馈 | 粘贴/文件 → AI 聚类 → 生成需求草稿 | 接收会议转入条目；批量 CSV/Excel 导入；来源标注；确认关卡（draft→confirmed） | 不做需求 CRUD（需求模块负责） |
| **需求** | 只读汇总页 | **统一中枢**：CRUD + 优先级 + lifecycle + 多来源 + 软删 + 筛选；→ API 带入 | 不做 API 生成（调用 API 模块） |
| API | 业务需求 → AI 生成 OpenAPI + 版本 + 导出 | 接受需求带入；自定义/手工草稿；模板库；按需求分组视图 | 不做 GraphQL/gRPC（v3） |
| 设置（新） | — | 模型选择 + Key 加密 + Provider 切换 | 不做团队级配置（v3） |
| 集成（新，P3） | — | 第三方凭证管理 + 外发回写 + Agent 执行引擎 | 不做双向实时同步（v3） |

## 4. 跨 Phase 技术债清理

PM 和代码调研都识别到 v1 有几个技术债，v2 应在合适的 Phase 顺手清理，避免债滚大。

### 4.1 LLM 调用入口统一（必做，Phase 2）

**现状**：LLM 调用存在两套并行实现：
- 前端：`src/lib/llm/provider.ts` + `dashscope.ts`（`LLMProvider` 接口 + `LlmError` 类）——**目前未被任何 server action 或 EF 使用**。
- EF 内：`supabase/functions/_shared/supabase.ts` 的 `dashscopeChat`（字符串错误码）——**实际在用**。
- `MODEL_BY_PURPOSE` 在三处重复定义（`provider.ts`、`_shared/supabase.ts`、各 EF 本地）。

**清理方案（Phase 2 随用户配置页一起做）**：
- EF 改为依赖 `_shared/` 内统一函数（已有，消除各 EF 本地重复）。
- 前端 `getLLMProvider()` 在 Phase 2 接入用户配置后，让 server action 走它（绕开 EF 的场景）。
- `MODEL_BY_PURPOSE` 改为单一来源：`_shared/model-config.ts`，EF 和前端都 import。
- 用户配置页能 override `MODEL_BY_PURPOSE`（按用户 `profiles.llm_config` 动态选模型）。

### 4.2 数据库类型生成（建议，Phase 2）

**现状**：`src/types/database.ts` 是手写占位，注释提到应改用 `supabase gen types typescript`。

**清理方案**：接入 `supabase gen types`，CI 里跑 `supabase gen types typescript --lang=typescript > src/types/database.ts`，保证类型与迁移同步。

### 4.3 文档约定对齐（轻量，Phase 1 顺手）

**现状**：`AGENTS.md` 声明了 `CONTEXT.md` + `docs/adr/` 约定，但实际未建立；架构决策散落在 `需求说明清单.md §9`。

## 5. 扩展机制设计（为 Phase 2/3 铺路）

### 5.1 用户级 LLM 配置（Phase 2）

```
profiles.llm_config (jsonb):
{
  "provider": "dashscope",          // dashscope | openai | custom
  "apiKey": "enc:xxxx",             // 应用层加密，UI 只显示 sk-****后4位
  "modelOverrides": {
    "extract": "qwen-max",          // 覆盖默认 MODEL_BY_PURPOSE
    "draft": "qwen-plus"
  },
  "baseUrl": "https://..."          // 自定义端点（私有化部署用）
}
```

**调用链**：server action / EF → 读取当前用户 `profiles.llm_config` → 覆盖 `MODEL_BY_PURPOSE` → 调 LLM。
**安全**：Key 用 Supabase Vault 或应用层 AES 加密，service_role 才能解密读；客户端永不返回明文。

### 5.2 第三方接入抽象（Phase 3）

统一抽象 `IntegrationProvider` 接口，每个第三方一个实现：

```typescript
interface IntegrationProvider {
  readonly type: 'jira' | 'feishu' | 'linear' | 'swagger';
  authenticate(credentials: IntegrationCreds): Promise<boolean>;  // "测试连接"
  pushRequirement(req: Requirement, mapping: FieldMapping): Promise<{ externalId: string; url: string }>;
  pushApiDraft(draft: ApiDraft): Promise<{ externalId: string; url: string }>;
}
```

**两阶段路线（用户已选"两者都做"）**：
- **外发（P3.1-3.3）**：server action 调 `IntegrationProvider.push*`，单向、可测、不破坏"人确认"原则。
- **内嵌执行（P3.4）**：接入 ZCode agent/mcp/skills，AI 自主提议建任务 → 落 `agent_execution_logs`（status=pending）→ 人审批 → 才执行。**审批流默认开启且不可关闭**（首月强制）。

## 7. 迁移与上线策略

### 7.1 数据迁移原则

1. **增量演进**：加字段不删字段，老字段保留兼容（如 `requirement_drafts.status` 保留，新增 `lifecycle` 接管业务状态语义）。
2. **保守回填**：老数据 `source_type='feedback_topic'` + `status='completed'` → 统一回填 `lifecycle='draft'`，**不自动置为 confirmed**，强制 PM 走查一遍（避免噪声当 backlog）。
3. **可回滚**：每个迁移前 `pg_dump` 备份受影响表；灰度期发现 Prompt 不稳定可回滚（保留字段，前端隐藏入口）。

### 7.2 各 Phase 上线方式

| Phase | 方式 | 理由 |
|---|---|---|
| **P1** | 功能开关灰度（白名单 → 第 2 周全量） | 涉及需求模块数据模型迁移 + 会议条目口径变更，需验证 |
| **P2** | 全量（配置项藏"高级设置"折叠区） | 增强性功能，无破坏性 |
| **P3.1-3.3** | 灰度（5-10 个 B 端团队先验 OAuth/Token） | 第三方凭证管理需真实环境 |
| **P3.4** | 白名单 + 审批流强制开启（首月不可关） | 改变产品原则，风险最高 |

### 7.3 风险登记册（摘要）

完整风险与缓解见 PM 补充材料，技术层面重点关注：

| 风险 | 等级 | 技术缓解 |
|---|---|---|
| 需求 lifecycle 语义错位（借用 gen_status） | 高 | 新增独立枚举 `requirement_lifecycle`，不复用 |
| 会议反馈转入造成用户困惑 | 中 | 转入文案 + 来源标注 + 已转入角标（可追溯链路） |
| 多来源优先级冲突 | 中 | 需求 priority 以"最近人工确认"为准，UI 显示来源对比 |
| Agent 执行引擎破坏"人确认"原则 | 高 | Propose-Approve-Execute 三段式，审批流默认强制 |
| LLM 配置 Key 泄露 | 高 | 应用层加密 + UI 脱敏 + service_role 才能解密 |
| meeting_item_category 扩展影响 Prompt/评测集 | 中 | P1 MVP 复用 issue 标记，P2 再扩枚举 + 重训评测 |
