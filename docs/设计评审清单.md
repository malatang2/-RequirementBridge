## 0. 一句话背景

需求阶段（SOW + 排期）与设计阶段（数据模型 / 接口契约 / UI 线框）产物已就绪，但存在一个**阻断性决策**：模型服务从 OpenAI 切换为国内通义千问（Qwen）系列——这一变更同时化解"音频/反馈数据出境"的合规风险（需求清单 Q1、数据模型 DM-4、接口 API-4），并需同步评估其对 4 份既有产物的影响。本次评审的核心就是**确认这一变更并冻结设计基线**。

> **评审原则**：所有项以"✅ 通过 / ⚠️ 有条件 / ❌ 否决 / ⏸ 挂起"四态裁决。**阻断项（🔴）任一无结论则 CP0 不放行**，下午不进入 M0 开发。

## 6. 【核心议题】模型服务迁移：OpenAI → 通义千问（Qwen）

### 6.1 迁移动机

| 维度 | OpenAI 方案 | 通义千问方案 | 结论 |
|---|---|---|---|
| **数据合规（Q1/DM-4）** | 音频/反馈送 OpenAI（境外），存在出境合规风险 | **DashScope 阿里云国内区域，数据不出境** | ✅ 千问直接化解阻断性风险 |
| 接口改造成本 | — | **DashScope 提供 OpenAI 兼容接口**，仅改 `base_url` + `api_key` | ✅ 迁移成本低 |
| 中文场景质量 | GPT-4o 中文良好 | Qwen 中文原生优化，会议/反馈场景更适配 | ✅ 千问占优 |
| 语音转写 | Whisper（境外） | Paraformer / fun-asr（中文 ASR，支持热词/说话人分离） | ✅ 千问占优（中文） |
| 成本 | GPT-4o + Whisper 双计费 | 国内模型定价通常更低；新用户有免费额度 | ✅ 千问占优（Q9 缓解） |
| 生态/可控 | OpenAI 闭源 | 可选开源版本（Qwen 开源）+ 云托管 | ✅ 灵活 |

> **核心论点**：本次切换**一举解决合规（Q1）、成本（Q9）两大阻断性问题**，且因 OpenAI 兼容接口存在，迁移成本可控。

### 6.2 模型映射（需评审拍板）

| 用途 | 原方案（OpenAI） | **建议方案（通义千问）** | 调用方式 |
|---|---|---|---|
| 会议结构化提取（决策/待办/需求/问题） | GPT-4o | **Qwen-Max**（能力对标，JSON 输出）或 **Qwen-Plus**（性价比） | DashScope OpenAI 兼容接口，`response_format` 强制 JSON |
| OpenAPI 3.0 生成 | GPT-4o | **Qwen-Max**（生成质量优先） | 同上 |
| 反馈聚类/情感/优先级 | GPT-4o | **Qwen-Plus**（量大，性价比优先） | 同上 |
| 需求草稿生成 | GPT-4o | **Qwen-Plus** | 同上 |
| **语音转写** | Whisper | **Paraformer-v2 / fun-asr**（录音文件识别，支持热词；说话人分离为 bonus，v1 不强制） | DashScope 异步转写 API |
| 图表 PNG 渲染（可选） | — | 与模型无关，前端 html2canvas | — |

**待评审决策项**：
- **D-M1**：默认主力文本模型选 Qwen-Max 还是 Qwen-Plus？（建议：生成类用 Max，聚类类用 Plus）
- **D-M2**：语音转写选 Paraformer-v2 还是 fun-asr？（建议：fun-asr，支持热词，会议术语识别更准）
- **D-M3**：是否启用 Qwen-Max 的"思考模式"？（结构化提取场景建议关闭以保证速度与 JSON 稳定性）
- **D-M4**（关键）：Supabase Edge Function（Deno，境外节点）调用 DashScope（国内）是否存在连通性/延迟问题？若不达标，是否将 AI 调用层迁至**阿里云函数计算 FC**（与 DashScope 同区域）？

### 6.4 迁移收益、风险与缓解

| 类型 | 项 | 说明 |
|---|---|---|
| ✅ 收益 | 合规达标 | 数据不出境，DM-4/API-4 阻断性问题解除 |

>   - 会议结构化提取（T1.3）、OpenAPI 生成（T2.2）：**Qwen-Max**——质量优先，JSON 字段稳定性最佳，对标 GPT-4o。
>   - 反馈聚类（T3.2）、需求草稿生成（T3.5）：**Qwen-Plus**——量大、性价比优先；聚类对"绝对精度"要求低于结构化提取，Plus 足够。
>   - 与 PM 倾向（生成类 Max / 聚类类 Plus）一致。**封装层（T0.5）以用途参数化模型名**（如 `LLMClient({ purpose: 'extract' | 'cluster' })`），便于未来调参不动业务代码。
> - **B3 ✅（语音模型）——选 fun-asr（paraformer-realtime-v2 / 录音文件识别版）**：
>   - **理由**：支持**热词**（会议术语、人名、产品名识别更准，直接提升"转录可读性 ≥4/5"与"原文引用可追溯率 ≥90%"两项验收），这是 Paraformer-v2 标准版不具备的。说话人分离（diarization）作为 bonus 不在 v1 强制（D3 已确认）。
>   - **调用方式**：录音文件识别为**异步任务**（提交→轮询→取结果），与现状机 transcribing 衔接需补 `asr_task_id`（见 A2.3 条件）。
>   - **备选**：若 fun-asr 在目标场景评测不达标，回退 Paraformer-v2（同 API 风格，迁移成本极低）。
> - **B4 ✅（思考模式）——结构化场景关闭思考模式**：
>   - 结构化提取（T1.3）、OpenAPI 生成（T2.2）强依赖**稳定 JSON + 低延迟**，思考模式会增加延迟与 token 消耗、并偶发破坏 JSON 结构。**默认关闭**（Qwen-Max 的 thinking 默认即不启用，确认参数显式不传 enable_thinking）。
>   - **例外**：复杂聚类（反馈量大、主题难分）可在 T3.2 探索性开启，但须有"关闭+重试"兜底。v1 建议聚类也关闭，先稳定基线。
> - **B5 ⚠️（网络连通，🔴 关键——给出明确处置，不悬置）**：
>   - **技术判断**：Supabase Edge Functions 运行在**境外（AWS 多区域，主要美东/美西/法兰克福等）**，DashScope 端点（`dashscope.aliyuncs.com`，杭州/北京）在国内。**出境调用入站可达**（Edge Function → 国内 API 在网络层通常通），但存在**延迟抖动、跨境链路稳定性、偶发超时**风险，对"50MB 音频 + Paraformer 异步轮询"场景影响可控（异步本身容忍延迟），对"同步结构化提取"场景需实测延迟。
>   - **裁决**：**v1 采用 Supabase Edge Function 方案**（保持单技术栈、迁移成本最低），**但 Day 2 内必须实测验证**（行动项#2）：跑一次完整链路（音频→fun-asr→Qwen 提取），记录 P50/P95 延迟与失败率。
>   - **降级路径（不达标时）**：将 **AI 调用层迁至阿里云函数计算 FC（与 DashScope 同区域杭州）**，Supabase Edge Function 仅做轻量编排（建库记录、转发）或前端直连 FC。**架构预留**：T0.5 封装层抽象 `LLMProvider` 接口，使切换 Provider（DashScope 直连 / 经 FC）不扩散到业务代码——这是用 0 成本买 B5 的保险。
>   - **结论**：**有条件 Go**——条件=Day 2 实测通过；不通过则按 §10 降级（先做不依赖 AI 的 M0 子任务），并启动 FC 迁移。**不构成 CP0 否决**。
> - **B6 ⚠️（产物同步修订，🟡 可降级）**：§6.3 四份文档改动点方向正确，认可。**但需注意改动量被低估**——实测需补充：

>   2. 状态机需补 `asr_task_id` 字段与超时落 failed 机制（见 A2.3）；
>   3. 数据模型 `openai_usage→llm_usage` 改名 + 内容结构 `{asr, llm}` 要明确 schema。
>   **结论**：认可改动方向，**条件**=行动项#1 回写时把上述 A2.2/A2.3 的遗漏一并补齐，并在 Day 2 内完成冻结。工时增量评估：原估 ≈0.5PD 偏乐观，实际约 **0.5–1PD**（含错误码映射表与状态机超时机制），仍在 T0.5/T1.2 吸收范围，**不改变 Day 2-6 里程碑**（与 B7 一致）。
